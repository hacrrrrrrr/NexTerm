# NexTerm

**Real Android terminal + browser terminal project.**

> Sponsorship / collaboration: **hunterkritik@gmail.com**

NexTerm is a native Android terminal project with a browser client for explicitly connected remote PTY sessions. It uses a real kernel-backed PTY rather than simulated command output.

## Browser pairing — user guide

NexTerm pairing is designed so users do not need to invent a token or WebSocket URL manually. A real Android NexTerm session generates a short-lived pairing payload, which can be shown as a QR code. The browser receives that payload and uses it to connect to the session gateway.

### User flow

    Android NexTerm
          |
          | Create browser pairing
          v
    Short-lived session
          |
          | QR: nexterm://pair?...
          v
       Scan QR
          |
          v
    NexTerm Web Browser
          |
          | WSS + session token
          v
    NexTerm Gateway
          |
          v
       Android PTY

### What the user does

1. Open NexTerm on Android.
2. Start the terminal/session that should be shared.
3. Open Browser Pairing / Connect Browser in NexTerm.
4. NexTerm creates a temporary pairing session. The default lifetime is 5 minutes.
5. Show the generated QR code on the Android device.
6. Open the NexTerm browser client on the phone, tablet or computer.
7. Scan the QR code, or paste the nexterm://pair payload into Connect to NexTerm → QR pairing payload.
8. The browser fills the endpoint and short-lived token automatically and attempts the WebSocket connection.
9. After successful authentication, the gateway binds the browser to the selected Android PTY.

### Manual testing

For development, the browser accepts a pairing payload such as:

    nexterm://pair?endpoint=wss%3A%2F%2Fgateway.example%2Fsession&session=demo-session&token=demo-token&expires=4102444800000

This is only a format/parser test. gateway.example is not a NexTerm gateway and will not create a terminal connection.

For a real development gateway, enter its WSS/WS endpoint and the short-lived session token generated by that gateway. Do not use localhost from a phone unless the gateway is actually running on the phone; use the computer's LAN IP for a local-network test.

### Where does the QR come from?

The Android pairing contract is implemented by PairingSessionManager. It generates a random session ID, a high-entropy token, an expiry timestamp and the nexterm://pair payload. A QR renderer can encode that payload without putting a permanent credential in the QR.

Important v0.5.7 limitation: the production WebSocket gateway and Android UI action that publishes a QR are still engineering work. The browser client can parse the pairing payload, but a payload by itself cannot create a terminal session. v0.6 is where the gateway/session service should make this end-to-end flow real.

### Security rules

- Pairing tokens expire after five minutes by default.
- Use WSS in production.
- Never put a long-lived API key in a QR payload.
- The gateway must validate the token, session ID and expiry server-side.
- Revoke a pairing token after successful handoff where practical.
- Treat a QR pairing code as a temporary bearer credential: anyone who obtains it may be able to use it before expiry.

## Two-in-one architecture

**Android:** Android UI → TerminalView → PTY → NDK → Android/Linux userspace.

**Browser:** Browser → authenticated WebSocket → NexTerm Gateway → PTY.

The browser does not fake a shell; a gateway/session must explicitly provide the PTY.

## Security

NexTerm must not expose a privileged Android shell to arbitrary web content. Production browser sessions should use short-lived credentials and an authenticated gateway. Do not place long-lived secrets in browser URLs.
